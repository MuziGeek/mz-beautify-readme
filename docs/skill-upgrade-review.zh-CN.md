# README Skill 优化：从规则到可检查成品

本轮把四个上游的有效做法接进实际工具和交付流程。固定的 oil-oil 核心、公共 MZ 路由、身份扩展边界和原有调用条件继续保留；未修改锁定快照。

## 融合后的具体变化

| 来源 | 吸收的能力 | 如何验证它真的起作用 |
| --- | --- | --- |
| oil-oil/beautify-github-readme | 从真实项目材料推导主题与构图 | 查看首屏是否展示产品真实输入、结果或素材；实际检查手机可读性 |
| BeatAPI/awesome-readme-studio | 事实来源排序、明确声明状态、比较封面方向 | 将重要宣传逐条核对到源码或输出；设计方向说明选择原因，不只换配色 |
| bmeunier1974/beautify-md | 区分原始度量与编辑判断 | 保存改造前后诊断；英文长句与中文字符分别统计，不用英语词数限制中文 |
| adewale/good-readme | 核对公开 API/CLI、执行真实使用示例 | 根据当前参数定义纠错，再运行正确命令；不能通过改源码迎合文档 |

详细来源、版本及未采用的做法见 [融合分析](../mz-beautify-readme/references/research-integration.md)。新增指导和工具为 MZ 实现，没有额外复制上游模板或脚本。

## 原有验收缺口

原资产校验器允许一个非空的 `validation` 对象充当验收记录，甚至只有 `safe: true`。旧预览工具只处理单张栅格图，无法发现整篇 README 的顺序、断链或手机显示问题。

现在，READY 资产清单必须关联 `mz.readme-review/1`。它检查当前 README、资产和证据的哈希，每种语言的桌面/手机、浅色/深色、正常/无图截图，以及与截图对应的实际观察。修改输入后，旧评审失效。语义事实、审美和用户满意度仍需要阅读、执行与真实反馈，脚本不冒充这些判断。

## 已实现的工具

- `resolve_visual_brief.py`：为公共 README 意图提供直接可运行的解析入口。
- `audit_readme_quality.py`：真正解析 Markdown；检查本地引用和图片说明，报告结构及英文/中文文案诊断。
- `render_readme_review.mjs`：真实打开离线页面，检查图片加载和页面溢出，输出每语言 8 个截图与完整 HTML。
- `validate_readme_review.py`：检查证据是否完整、是否仍对应当前文件；初始化只产生未核实草稿。
- `validate_asset_manifest.py`：READY 必须附带上述评审，布尔字段不能跳过验收。

命令、依赖和数据字段见 [验收操作说明](../mz-beautify-readme/references/review-evidence.md)。旧 v3 草稿仍可读取；旧版仅布尔值的 READY 清单需要重新生成证据。这是有意收紧的完成条件。

## 实用样例

本轮使用 Linepack 小型 Python 工具作为隔离样例。输入是带空行的文本，实际输出是两条带原始行号的 JSON 记录。原说明含错误参数和缺乏实现依据的功能宣传；改造时依据参数解析器修正使用方式，以实际输出替换宣传，并生成中英文桌面与手机 SVG。

原始测试任务可复现：

```text
python tools/create_evaluation_fixture.py NEW_EMPTY_EVALUATION_DIRECTORY
```

对生成目录调用新版 Skill，执行完整 README 改造。产品源码只读；需要改变的对象是文档和资产。原始资料是故意保留缺陷的测试输入，不是可发布产品介绍。

本轮检查也发现并修复了一个预览假阳性：HTML 字符串可以被截图，却没有正确的本地图片基础路径。现在工具会实际打开文件、等待图像解码并核对自然尺寸；测试同时覆盖图片损坏、嵌套路径和深浅主题素材选择。

独立源码分析由 Luna Medium 完成；预览工具由 Terra High 实现，经主线程复核后修正。独立实用测试由 Terra High 启动，但中途遇到模型容量不足；剩余样例生产与验收由主线程接管。本轮不能记作完整独立盲测通过，也不能由一个小型工具样例推断所有产品类型均已验证。

## 结果边界

自动测试验证文件、渲染和证据契约，不计算“美观分”。本地页面是 GitHub 风格近似；远程资源、线上 GitHub 过滤及外部服务需要另行验证。当前工作没有提交、推送或发布。用户是否满意，以其查看成品后的明确反馈为准。
